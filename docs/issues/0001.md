# 0001 — Stop `is_exhausted` from disarming asyncio's unretrieved-exception warning

**Status:** Open
· **Kind:** Bug
· **Parent:** <a href="README.md" title="Issues">Issues</a>
· **Related:**
  <a href="0002.md" title="0002 — Make a timed-out read leave the select alive">0002</a>

> Every task `aselect` hands to a consumer arrives with asyncio's
> "Task exception was never retrieved" warning **already switched off**. A
> consumer that receives a failed task and forgets to inspect it gets no
> exception, no warning, and no report to the event loop — the source's failure
> vanishes completely.
>
> The cause is one line: `is_exhausted` calls `task.exception()` to test for
> `StopAsyncIteration`, and `Task.exception()` clears the private
> `_log_traceback` flag that asyncio uses to decide whether to complain at
> collection time. `ataskify` and `amerge` both call `is_exhausted` on every
> pull, so the flag is cleared before the consumer ever sees the task.
>
> This matters more than an ordinary rough edge because it undercuts
> `ataskify`'s reason for existing. The whole point of yielding tasks instead of
> values is that **the consumer decides** what to do with a failure. The safety
> net for a consumer that decides nothing is switched off by the very mechanism
> that offers the choice — and silence is indistinguishable from success.

## Background

`ataskify` wraps a value-yielding async generator so that its pulls come out as
already-completed `asyncio.Task` objects. The consumer's `await` is what turns
one back into a value, or re-raises whatever the source raised producing it:

```python
async for task in ataskify(source()):
    try:
        item = await task
    except SomeError:
        ...  # the consumer's call
```

`aselect` is built on that, so it yields `(key, task)` pairs.

Both layers need to know whether a completed pull means "the source ran out"
rather than "the source failed", and `is_exhausted` is how they ask
([`_pulling.py`](../../turbopipes/_pulling.py)):

```python
def is_exhausted(task: asyncio.Task[_T]) -> bool:
    return not task.cancelled() and isinstance(task.exception(), StopAsyncIteration)
```

`task.exception()` is the natural way to write that. It also has a documented
side effect: retrieving a task's exception marks it retrieved. In CPython that
is `Task._log_traceback = False`, and `Task.__del__` consults exactly that flag
when deciding whether to call `loop.call_exception_handler` with
`'Task exception was never retrieved'`.

So the check is not read-only. It consumes the very signal that protects a
careless consumer.

### Measured, with a control

Run against `9a78e18` on CPython 3.14.6. **(a)** is the control — the same
failed task, dropped without `is_exhausted` ever touching it:

```
5(a)  CONTROL: drop a failed task nobody ever inspected
       _log_traceback=True
       !! loop.call_exception_handler: 'Task exception was never retrieved' exc=RuntimeError('ctl exploded')
       loop reports: ['Task exception was never retrieved']

5(b)  same, but is_exhausted() looked at it first (as turbopipes does)
       _log_traceback before=True
       is_exhausted(task) -> False
       _log_traceback after =False
       loop reports: NONE

5(c)  end to end: ignore a failing task handed out by real aselect
       aselect handed out ('bad', task); a careless consumer never awaits it
         task._log_traceback=False
       loop reports: NONE
         ^ a source failure that reached the consumer and was dropped: SILENT

5(d)  contrast: the same failure through amerge (no ataskify)
       amerge RAISED RuntimeError('bad exploded')  <- impossible to ignore
```

**(d) is the part that stings.** The identical source failure is impossible to
miss through `amerge`, and completely silent through `aselect` — so moving up to
the richer primitive is what loses the diagnostic.

## Proposal

Test for exhaustion without retrieving the exception, then restore nothing —
there is nothing to restore, because the flag was never cleared.

`asyncio.Task` exposes no public read-only accessor for a completed task's
exception, so the options are:

1.  **Re-arm the flag after looking.** Call `task.exception()` as today, then
    set `task._log_traceback = True` when the exception was *not*
    `StopAsyncIteration`. Smallest diff; reaches into a private attribute, and
    the name is CPython-specific.
2.  **Don't inspect the task at all — track exhaustion out of band.** The layer
    that armed the pull knows what it armed; a source that raised
    `StopAsyncIteration` could be recorded when the pull is created rather than
    interrogated when it completes. Larger change, no private attribute.
3.  **Hand out a wrapper rather than the raw `Task`**, so the library controls
    what "retrieved" means. Largest change, and it gives up the property that
    the consumer holds a genuine `asyncio.Task`.

(1) is the pragmatic fix and (2) is the clean one; this issue does not pick.
Whichever lands, the acceptance below is the same.

## Non-goals

- Changing what a consumer is *supposed* to do with a task. Ignoring a failed
  task stays a consumer bug — this issue is only about whether Python is still
  allowed to say so.
- Making `aselect` raise on a source failure. That is `amerge`'s contract, and
  the difference between them is deliberate.

## Acceptance

- The control above (**5a**) and the through-`aselect` case (**5c**) produce the
  **same** loop report. Today one warns and the other is silent.
- A consumer that *does* inspect the task — the ordinary case — still sees no
  spurious "never retrieved" report.
- `is_exhausted`'s own behaviour is unchanged for every input: cancelled tasks,
  `StopAsyncIteration`, other exceptions, and successful results.
- A regression test asserts the loop report, not just the flag, so a future
  refactor that reintroduces the clearing is caught.

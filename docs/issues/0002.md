# 0002 — Make a timed-out read leave the select alive

**Status:** Open
· **Kind:** Bug
· **Parent:** <a href="README.md" title="Issues">Issues</a>
· **Related:**
  <a href="0001.md" title="0001 — Stop `is_exhausted` from disarming asyncio's unretrieved-exception warning">0001</a>,
  <a href="0003.md" title="0003 — Give `abuffer` a teardown path that cannot deadlock, before writing one that can">0003</a>

> Wrapping a read from `aselect` in `asyncio.timeout()` **destroys the select**.
> The first read times out as expected; the second raises
> `StopAsyncIteration`, and every source the select was watching has been torn
> down. There is no error and no warning — the loop simply ends, exactly as it
> would on a clean end of stream.
>
> This is the first thing a user reaches for. "Wait for whichever source speaks
> next, but give up after a second and do something else" is the archetypal
> reason to want a select at all, and the archetypal spelling of it is a
> timeout around the read.
>
> The cause is structural rather than a slip: the armed pulls live in the
> select's own generator frame, so cancelling the read unwinds that frame and
> takes the arms with it.

## Background

`aselect` merges several keyed sources and yields from whichever produces
first:

```python
async for key, task in aselect({'a': source_a(), 'b': source_b()}):
    ...
```

To do that it must have a pull outstanding on *every* source at once — it arms
one per source, waits for the first to complete, yields it, and re-arms. Those
armed pulls are local state inside the generator's frame, held across the
`yield`.

That is what makes a timeout destructive. `asyncio.timeout()` works by
**cancelling** the coroutine awaiting inside it. When that coroutine is
`anext(sel)`, the `CancelledError` is delivered *into the select's frame* — so
it unwinds, the arms it was holding are cancelled with it, and the generator
finishes. The frame is gone, which is why the next call reports a clean end of
stream rather than an error: from the outside, an exhausted generator and a
destroyed one are the same object in the same state.

### The idiom, and what it does

Run against `9a78e18` on CPython 3.14.6, with one source that takes 20 ms per
item and a 5 ms timeout:

```
attempt 0: timed out; trying again...
attempt 1: StopAsyncIteration -- SELECT IS DEAD
sel.ag_frame is None -> True
```

The source had two more items to give. Nobody is told.

### Working case, for contrast

Hand-driving `anext()` on a *held* select — no timeout — behaves exactly like
`async for` over it: same items, same order, same round-robin fairness. So
one-shot reads are fine; it is specifically **cancelling** one that is fatal.

The distinction that decides this is *where the arms live*. A select whose arms
sit in a generator frame dies with the frame. A select whose arms sit in an
ordinary object outside the frame does not — `asyncio.wait` does not disturb
what it waits on, so cancelling the waiter leaves the arms intact and the
sources untouched. That was measured too, on a prototype:

```
armed keys: ['fast', 'slow']; cancelling the pending read
after cancel: still armed -> ['fast', 'slow']  (sources untouched)
  got fast='fast0'  <- NOTHING WAS LOST
```

## Proposal

Three directions, in increasing order of cost. This issue does not pick one.

1.  **Document it and give the working spelling.** Cheapest, and worth doing
    regardless of what else lands: `aselect`'s docstring should say that
    cancelling a read ends the select, and show the alternative — arm the read
    yourself with `asyncio.ensure_future(anext(sel))` and apply the timeout to
    *that*, so the timeout cancels a future you own rather than the generator.
2.  **Shield the arms.** Keep the generator shape but stop a `CancelledError`
    arriving at the `yield` from taking the armed pulls down with it. Needs
    care: the whole teardown story currently depends on cancellation
    propagating, so this risks trading a lost select for a leaked source.
3.  **Offer a state-object select** whose arms live outside any frame — a
    `Select` holding a dict of armed pulls, read one at a time. Immune by
    construction, and it is the only shape that can also express a synchronous
    `peek()` and *decline* a pass (Go's `select` with a `default:`). Its honest
    cost is that it is a **second ownership model** standing beside "the
    generator is the handle", and it does not compose with `async for`.

(1) is not a fix and should not be treated as one — a documented footgun is
still a footgun. It is listed first because it can land today.

## Non-goals

- Making cancellation *non-destructive in general*. Cancelling an in-flight
  `__anext__()` ends any async generator, not just this one; that is Python's
  behaviour and is out of scope.
- Adding a timeout parameter to `aselect`. That solves one instance of the
  shape and leaves the general case ("give up on this read for any reason")
  just as broken.

## Acceptance

- The idiom above — `asyncio.timeout()` around a read, repeated — either works,
  or fails loudly. **Silently returning `StopAsyncIteration` from a select with
  live sources is the specific outcome to eliminate.**
- Whatever lands, a regression test covers the two-attempt sequence and asserts
  the second attempt still yields an item.
- Teardown properties are unchanged: breaking out of the loop, closing the
  select, and cancelling the consuming task all still finalize every source and
  leave no pending tasks.

# 0003 — Give `abuffer` a teardown path that cannot deadlock, before writing one that can

**Status:** Open
· **Kind:** Enhancement
· **Parent:** <a href="README.md" title="Issues">Issues</a>
· **Related:**
  <a href="0002.md" title="0002 — Make a timed-out read leave the select alive">0002</a>

> **Nothing is broken today — `abuffer` does not exist yet.** This issue exists
> so that the trap found while prototyping one is written down before somebody
> writes the obvious version and ships it.
>
> A buffering wrapper lets a source run ahead of its consumer. The natural
> implementation is a pump task filling an `asyncio.Queue`, forwarding
> exceptions into the queue as envelopes. That version **hangs on `aclose()`**,
> but only when three things coincide: the buffer is full, the source raises
> from its own cleanup, and the pump happens to be parked on one particular
> `await` rather than another.
>
> It is the shape of bug that passes every test and wedges in production. The
> fix is one flag and is given below.

## Background

Everything in turbopipes today is **0-deep**: a source computes item *N+1* only
once the consumer asks for it. Three items at 50 ms to produce and 50 ms to
consume take 306 ms — fully serialized, because between hand-offs the producer
is not slow, it is *not running*.

A buffer changes that by giving the producer its own scheduling:

```
bare async generator (0-deep baseline)  TOTAL 306 ms
abuffer(capacity=1)                     TOTAL 205 ms
```

The price is fixed and worth stating plainly, because it is what this issue is
really about: **depth requires an independently scheduled producer, which is a
thing that can outlive its consumer, which is exactly the entity that needs
supervision.** A prototype confirmed the whole ownership model survives — but
only after the deadlock below was found and fixed.

### The broken case

The natural pump: iterate the source, `put` each item, forward an exception into
the queue as an envelope, `put` an EOF envelope at the end. On teardown the
wrapper cancels the pump via `asettle`.

Now let the source raise from its own `finally` in response to that cancellation
— a cleanup failure, which is a case turbopipes already has machinery for. The
`RuntimeError` *replaces* the `CancelledError`, the pump's `except Exception`
catches it, and the pump tries to `put` it into a queue that is full and that
nobody is draining any more, because the consumer is gone.

Same source, same failure; the outcome depends only on where the pump was
parked:

```
buffer NOT full, pump parked in anext()   cancelled=False done=True exc=None
                                          queue holds 1 item, 1 exc envelope
buffer FULL,     pump parked in put()     pump ended RuntimeError    <- correct
buffer FULL,     pump parked in anext()   **WEDGED**: still pending 1 s after cancel()
                                          parked at `await queue.put((EXC, exc))`
                                          a SECOND cancel() broke the wedge
```

`asettle` issues exactly one `cancel()` per task, so the third row is a real
hang and not a hypothetical. At the wrapper level, with an ordinary consumer
under `contextlib.aclosing`:

```
aclose() with a FULL buffer + failing source cleanup  ->  **aclose() HUNG**, still pending 1 s later
aclose() with room in the buffer                     ->  returned; failure vanished entirely
                                                         (no warnings, no loop reports)
```

Both outcomes defeat the existing cleanup-reporting machinery: the pump reports
success after being cancelled, and the cleanup failure sits unread in a queue
that is about to be discarded.

### The fix

One shared flag — "nobody is draining any more" — set *before* `asettle`
cancels, so the pump never blocks on `put()` once the consumer is gone, and
re-raises rather than swallowing during teardown (sketch):

```python
async def _pump(gen, queue, state):
    async with contextlib.aclosing(gen):
        try:
            async for item in gen:
                await queue.put((ITEM, item))
        except Exception as exc:
            if state.closing:
                raise                       # hand it to asettle; never block on put
            await queue.put((EXC, exc))
        else:
            if not state.closing:
                await queue.put((EOF, None))


async def abuffer(gen, capacity=1, *, label=None):
    queue = asyncio.Queue(maxsize=capacity)
    state = _PumpState()
    task = asyncio.create_task(_pump(gen, queue, state))
    try:
        while True:
            kind, payload = await queue.get()
            if kind == ITEM:
                yield payload
            elif kind == EOF:
                break
            else:
                raise payload               # original exception, traceback intact
    finally:
        state.closing = True
        await asettle([task], label=label)
```

With that, eleven teardown scenarios at capacities 1 and 4 came back clean —
break-early, walk-away-without-`aclose`, upstream failure mid-stream (arriving
in stream order with the traceback intact), consumer cancelled mid-`anext`,
source cleanup that raises or awaits, and composition under `ataskify` /
`amerge`. Zero live tasks in every case.

## Proposal

If and when `abuffer` is built:

- Use the shared-flag shape above, or something else that provably cannot block
  on `put()` after the consumer is gone. **Do not ship the obvious version.**
- **Depth is `capacity + 1`, not `capacity`** — the pump holds one further item
  in hand while parked in `put()`. Verified: capacities 1/2/4/8 give
  max-in-flight 2/3/5/9.
- **Reject or remap `capacity=0`.** By analogy with Go's `make(chan T)` it
  reads as "rendezvous", but `asyncio.Queue(maxsize=0)` is *unbounded* — a
  probe duly ran 19 of 20 items ahead.
- Route a discarded exception envelope to the loop exception handler on
  teardown, so a failure discovered while running ahead is not silently lost.

## Non-goals

- Deciding *whether* to build `abuffer`. That is a separate call, and the two
  inherent costs below are the substance of it.
- Queue interop (`queue_to_gen` / `gen_to_queue`). Related, separately shaped.

## The two costs that are inherent, not bugs

These belong in the docstring rather than the tracker, and are recorded here so
the decision above is made with them in view. They cannot be engineered away,
because they *are* depth:

- **Buffered items are discarded silently on early exit.** At capacity 4:
  produced `[0,1,2,3,4]`, delivered `[0]`, and `[1,2,3,4]` dropped with no
  diagnostic. With a bare generator those items would never have been produced.
  Where producing has side effects — an HTTP request, an advanced DB cursor, a
  consumed Kafka offset — **buffering has already committed them**, and it is
  invisible at the call site.
- **A failure discovered while running ahead can vanish.** Source fails at item
  2, consumer walks away after item 0: the failure genuinely happened, was
  captured, and was thrown away, with the consumer exiting cleanly.

## Acceptance

- A test that reproduces the wedge against the naive implementation — full
  buffer, failing source cleanup, pump parked in `anext()` — and passes against
  the real one.
- `aclose()` returns in every combination of {buffer full, buffer with room} ×
  {clean source, source whose cleanup raises}, and the cleanup failure is
  reported exactly once.
- Depth and the `capacity=0` handling are asserted, not just documented.
